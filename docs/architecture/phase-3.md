# Phase 3: Core School Domain

Phase 3 adds the records every later module builds on: the school's academic structure, its people, enrollments and teaching assignments. Everything runs on the Phase 2 security foundation: the same authentication, tenant resolution, permissions, data scopes, RLS and audit. Phase 3 adds no second authorization mechanism.

Decisions: ADR-022 (grades and sections), ADR-023 (profiles link to memberships), ADR-024 (scoped resource endpoints). Entity details are in [docs/domain/](../domain/).

## Domain model

```
School (tenancy.School — profile, address, timezone, settings)
 ├── Campus
 ├── Department
 ├── Grade  ("class": Grade 5, Class X, KG-1 — stable across years)
 ├── AcademicYear  (planned → active → closed; no overlap; one current)
 │     └── Section  (Grade × Year, e.g. 5-A 2026-27; optional campus; capacity)
 │           ├── Enrollment ── Student
 │           └── TeacherAssignment ── StaffProfile (teacher) ── Subject?
 ├── Subject  (optional department)
 ├── StaffProfile ── Membership ── User          (teachers: staff_type = teaching)
 ├── Student ── Membership? ── User               (only students who sign in)
 └── Guardian ── Membership? ── User
        └── StudentGuardian ── Student            (many-to-many, primary, emergency contact)
```

| Module | Tables |
|---|---|
| `tenancy` | `tenancy_school`, extended with legal and short name, contacts, address, timezone and settings |
| `academics` | `campus`, `academic_year`, `department`, `grade`, `section`, `subject` |
| `people` | `staff_profile`, `student`, `guardian`, `student_guardian`, `enrollment`, `teacher_assignment` |

`people` depends on `academics`; `academics` never imports `people`. Relationship-based scope rules for sections are registered by `people` (it owns the relationships).

## Identity versus domain

- **Credentials and sign-in stay in Phase 2** (`identity.User`, OTP, tokens). No Phase 3 table stores a password, OTP or token.
- **A profile of someone who signs in points at their `Membership` in this school**, not at the user. A user can be a teacher in one school and a parent in another; each school sees only its own membership and profile.
- **Teacher = role + profile.** The `teacher` role grants permissions; the `StaffProfile` (with `staff_type = teaching`) is the domain record that teacher assignments refer to.
- **Students and guardians may have no login.** `membership` is optional for them; the profile still exists, with guardian contact details stored on the guardian.

## Tenant boundaries and integrity

Every Phase 3 table is school-owned (`school_id`, non-null, indexed). Cross-tenant combinations are rejected at three layers:

| Layer | Mechanism |
|---|---|
| Service | Every client-supplied reference is resolved with `tenancy.domain.resolve(model, actor.school, id)`. Another school's ID answers exactly like an unknown ID (`400`, same message). |
| Database | **Composite foreign keys** `(x_id, school_id) → x(id, school_id)` on every cross-table reference (people migration 0002, academics migration 0002). |
| Database | **RLS** `tenant_rw` on every table (the same policy as Phase 2, generated by `eduflow.core.rls.tenant_rls`). |

Key composite keys:

- `enrollment (section_id, academic_year_id, grade_id, school_id) → section (id, academic_year_id, grade_id, school_id)`. An enrollment's section always belongs to its grade, its academic year and its school.
- `teacher_assignment (section_id, academic_year_id, school_id) → section (…)`. An assignment's year is its section's.
- `staff_profile / student / guardian (membership_id, school_id) → membership (id, school_id)`.
- `student_guardian (student_id, school_id)` and `(guardian_id, school_id)`.
- `section (academic_year_id, school_id)`, `(grade_id, school_id)`, `(campus_id, school_id)`; `subject (department_id, school_id)`; `staff_profile (department_id, school_id)`, `(campus_id, school_id)`.

## Important business rules

| Rule | Enforced by |
|---|---|
| Academic year: `start_date < end_date` | `CHECK` + service |
| Academic years of a school never overlap | `EXCLUDE USING gist (school_id =, daterange &&)` + service pre-check |
| At most one current year per school; only an active year can be current | partial unique index + `CHECK` + service |
| Year lifecycle `planned → active → closed`; only planned years can be deleted | service |
| **Closing a year** completes its active enrollments and ends its active teacher assignments (audited), so nobody keeps access to students through a finished year. Its sections, enrollments and assignments are then read-only. | `academics.services.year_closing` signal, handled by `people.services.wind_down_year` |
| A student whose status leaves `active` has their active enrollment ended (`graduated` → completed, otherwise withdrawn) | service |
| Enrollment start, end and transfer dates fall within the academic year | service |
| Grade, campus, department and subject codes and (case-insensitive) names are unique per school | unique constraints |
| Section code and name unique per (year, grade); capacity > 0 and never below current enrollment | constraints + service |
| No new sections, enrollments or assignments in a closed year | service |
| One **active** enrollment per student per academic year | partial unique index |
| Roll numbers unique among active enrollments of a section | partial unique index |
| Enrollment lifecycle `active → completed / withdrawn / transferred` (terminal); end date required when not active | `CHECK` + service |
| Transfers stay within the academic year and link old → new | service + `CHECK` |
| One primary guardian per student; a guardian linked once per student | partial unique + unique |
| One active class teacher per section; no duplicate active (teacher, section, subject) | partial unique indexes |
| Only active *teaching* staff can be assigned, to active sections and subjects; `left` or a change to `non_teaching` ends the person's active assignments (each audited) | service |
| Ended assignments and closed-year records are history: they cannot be edited or deleted | service |
| Students and enrollments are never hard-deleted through the API | no `DELETE` permission (403) |
| In-use structure cannot be deleted (archive instead) | `PROTECT` foreign keys → `409` |

## Authorization and data scopes

19 new permissions (`campus`, `academic_year`, `department`, `grade`, `section`, `subject`, `guardian`, `enrollment`, `teacher_assignment` × `read`/`manage`, plus `staff.create`). Existing `student.*` and `staff.*` permissions are reused. The full table is in [authorization.md](../security/authorization.md#phase-3-domain).

| Role | Reach in Phase 3 |
|---|---|
| Platform Admin | `/platform/schools` (profile, activation). **No** implicit access to school data (ADR-003). |
| School Admin, Principal | Everything in their school (manage and read) |
| Teacher | Structure (school-wide read); **sections they teach** and those sections' students, enrollments, guardians and co-teachers; their own staff record |
| Parent | Structure; **their children** and the children's enrollments, sections and teachers; their own guardian record |
| Student | Structure; **themselves**, their enrollment, section, teachers and guardians |
| Accountant, librarian, transport and hostel managers | Students, sections and enrollments school-wide (read) |
| HR Manager | Staff (read, create, update) school-wide |

**Writes need the write permission school-wide.** A write references other records (sections, students, memberships) that a narrower scope cannot vouch for, so a section- or self-scoped `*.manage` grant authorises no write in Phase 3. Narrower write scopes come with the modules that need them (attendance). **Linking an account** (membership) to a student, guardian or staff profile also needs school-wide `user.update`, and nobody can link their own account, because the link decides who gets `self` and `child` scope.

The scope rules are declared once, in `people/policies.py`, as `ScopedResource` rules (section, child, self, campus, department). Views never mention roles. A scope without a rule grants nothing, so it fails closed.

## API

All under `/api/v1/`, all with `Authorization` and `X-School-Id`:

| Resource | Endpoints |
|---|---|
| School profile | `GET/PATCH /school`; platform: `GET/PATCH /platform/schools/{id}` |
| Structure | `/campuses`, `/academic-years`, `/departments`, `/grades`, `/sections`, `/subjects`: list, create, retrieve, update, delete |
| People | `/staff`, `/students`, `/guardians`: list, create, retrieve, update |
| Guardianship | `/student-guardians`: list, create (link), retrieve, update, delete (unlink) |
| Enrollment | `/enrollments`: list, create, retrieve, update; `POST /enrollments/{id}/end`, `POST /enrollments/{id}/transfer` |
| Teaching | `/teacher-assignments`: list, create, retrieve, update, delete |

- **Lists** are cursor-paginated (`?cursor=`, `?page_size=` up to 200, newest first) and filterable (for example `/sections?academic_year_id=&grade_id=&campus_id=&status=`, `/students?section_id=&academic_year_id=&status=`). Filters only narrow the caller's scoped queryset; a filter value from another school returns an empty list, and an invalid value is `400`.
- **Grades are at `/grades`**, not `/classes`: the existing client already uses `/classes/{id}` for sections (ADR-007, ADR-022).
- **Teachers** are `/staff?staff_type=teaching`.
- Payloads use IDs plus compact one-level references (`{"id","name","code"}`). There are no recursive nests and no identity fields beyond a display name.

## RLS strategy

All 12 Phase 3 tables have RLS enabled with the standard `tenant_rw` policy, created by migration and generated by one helper (`eduflow.core.rls`), so a new table cannot get a different policy. `people/tests/test_rls.py` checks, for **every** table: the policy exists; no tenant context means no rows; tenant A reads only A; A cannot update or delete B's rows or insert into B. The smoke test repeats the "no context" check on the running stack.

## Audit

Every write is audited through the Phase 2 service (`audit.record`):

- `academics.<entity>.created|updated|deleted`
- `people.staff|student|guardian.*`
- `people.guardian.linked|unlinked|link_updated`
- `people.enrollment.created|completed|withdrawn|transferred|updated`
- `people.teacher_assignment.*`
- `tenancy.school.updated`

Metadata lists the changed field names and key references, never field values.

## Performance

- Indexes lead with `school_id` and follow the list filters (section by year and grade; enrollment by section and status, and by student and status; assignment by staff and by section).
- List views `select_related` everything they render. A query-count test asserts that each list's query count does not grow with the number of rows.
- Scope rules are pure SQL (`EXISTS`-style subqueries), with no per-row lookups.

## Not in Phase 3

Timetable, attendance, lessons, homework, assessment, report cards, analytics, communication, transport, hostel, library, payroll, billing, AI, promotion between years, terms and rooms. Phase 3 provides the keys they will reference: section, subject, teacher assignment, enrollment and academic year.
